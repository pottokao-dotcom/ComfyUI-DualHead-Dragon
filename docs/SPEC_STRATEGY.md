# 草稿加速策略：樹狀驗證（DFlash2）

> 狀態：2026-09-30 做完第一版，分支 `spec-strategy`。節點預設 `draft_tree` 20（使用者同意）；Python `generate()` 預設 0。
> 每條結論都標了 **【實測】** 或 **【推論】**。
> 研發過程的逐筆紀錄在 blackhole `~/dflash_8b_gguf/SPEC_STRATEGY_MODULE_PLAN.md` 第 8 節（含走過又放棄的路）。

## 0. 一句話

每輪本體要驗證幾個草稿字，成本幾乎只看「一次驗幾個字」。原本這筆預算全押在草稿的一條主線上；
現在改成押在**草稿最有把握的幾條路**：草稿不確定的地方同時押第 2、3 名，或在不同位置各開一條分支。
本體照樣一格一格抽字、對上才接受，所以**輸出分佈完全不變**，只是每輪前進更多。

## 1. 怎麼用

- **Dual-Head Rewrite** 節點：`draft` 選 DFlash2 草稿，`draft_tree` 預設 20（0 = 關，只押一條主線）。
- Python：`backend.generate(..., draft=..., draft_n_max=15, draft_tree=15)`。
- 只對 **DFlash2** 草稿有效（要選擇器 lattice）；其他草稿型別自動走原本的主線。
- 建議值（blackhole RTX 5060 Ti，見第 4 節）：`draft_n_max` 15、`draft_tree` 20。別的卡請用第 5 節的工具量一次。

## 2. 原理

DFlash2 的選擇器每格給 16 個候選字，外加一張「前一格選第 i 名 → 這格各候選」的 16×16 分數表（lattice）。
原本的草稿 = 沿這張表每格取第一名的那條路。

`native/dh_tree.cpp`：從根開始做**最佳優先展開**——所有候選路徑依「整條路的草稿機率」排隊，每次取最大的一個節點加進樹，
直到用完預算。所以「主線再押深一格」和「這格改押第 2 名」是公平競爭，誰機率大押誰。枝數（葉子數）不超過節點 context
的序列數（1 + prefix_slots = 5）。

`native/dh_spec.cpp` 每輪：
1. 每片葉子一條 KV 序列（0..4；1..4 借用 system prompt 快取槽，帶草稿生成結束後本來就會清），每個節點標上它底下所有葉子的序列，
   整棵樹一次送本體驗證。前綴先 `seq_cp` 到各序列（unified KV 只改標記，不複製資料）。
2. 本體從根一格一格抽（greedy 或抽樣都一樣），抽到的字是哪個子節點就往下走，對不上就停。
3. 接受的那條路搬回序列 0，其他序列清掉；草稿只補吃根 + 接受的路。

llama.cpp 只改兩件小事（`patches/0003-dflash2-tree-hooks.patch`，約 40 行）：
- 把每輪的 lattice 交出來：`dh_dflash2_lattice()`。
- DFlash `process()` 原本假設同一序列的列在批次裡是連續的；改成逐列收集（接受的路在樹批次裡是跳著的）。一般用法行為不變。

## 3. 實測（blackhole RTX 5060 Ti，GPU0，QI2.1 TE DHQ Q4_K_M + v4.1 大師 LoRA，run4 16k 草稿，heldout 30 題，節點預設抽樣 temp 0.7）

**【實測】** 研發時的實驗版 lib（跟正式模組同演算法；正式模組的數字在第 4 節）：

| 設定 | 每輪前進 | tok/s | 對押 7 |
|---|---|---|---|
| 押 7，不開樹（三次：131.3 / 129.8 / 128.2） | 3.51 | 129.8 | — |
| 樹 7 | 3.86 | 140.8 | +8.5% |
| 樹 11 | 4.36 | 143.3 | +10.4% |
| 樹 15 | 4.55 | 145.2 | +11.9% |
| 樹 20 | 4.67 | 148.2 | +14.2% |
| 草稿算 15 格 + 樹 15 | 4.73 | 149.3 | +15.0% |

- **【實測】** 樹狀每輪多花的時間很少：樹 7 比押 7 每輪多 0.5 ms（26.3 vs 25.8 ms），因為一次驗證、草稿只補吃一次。
- **【實測】** 抽樣下草稿把握度仍然準（說 0.5 中 0.47、說 0.9 中 0.90），所以用草稿機率排路徑是對的。
- **【實測】** 樹 7 的形狀：一個分叉點 56%、兩個 21%、沒分叉 22%；單點押 2 把 54%、3–4 把 24%。只押「一條分支、第 2 名」的舊版實測只打平（+0.9%）。
- **【推論】** 不同顯卡的最佳預算可能不同：本體 decode 越快，驗證相對越貴。blackhole 與 gx10 都是 20（第 4 節）；moon（5070 Ti）待量。

## 5. 工具（`tools/spec_tree/`）

| 檔案 | 用途 |
|---|---|
| `bench.py` | 測速 + 存輸出；`--tree N` 開樹、`--lat` 存每輪 lattice、`--repo` 指定節點程式碼 |
| `check.py` | 開樹的正確性檢查（實機接受數 vs 離線重建） |
| `sim.py` | 離線比較各種押法每輪前進多少（押幾格、樹預算）；`--cost` 給價目表可估 tok/s |
| `latio.py` | lattice 檔讀取 + 建樹/對答案函式（跟 `dh_tree.cpp` 同演算法） |

換一張卡選預算：`bench.py` 跑 `--tree 0 / 7 / 15 / 20`（各 30 題約 4 分鐘），取最快的。

## 6. 試過、不做的

- **動態押注**（每輪依把握度決定押幾格）：8 字以內驗證價格幾乎一樣，模擬每輪都選滿；超過 8 字時換形狀的 CUDA graph 費用吃掉好處。【實測】
- **一條分支（第 2 名 + 接幾格）**：抽樣下 +0.9%，打平。【實測】
- per-shape CUDA graph（給動態押注用）：固定預算時用不到。
- 片語表 / 滑窗 / top_k / 草稿 Q3 以下：之前驗證過沒用。

## 7. 限制

- 只支援 DFlash2 草稿；只在純文字 prompt 走草稿（帶圖的 I2I 仍走一般生成）。
- 枝數 ≤ 節點 context 序列數（預設 5）。
- 預算上限 31（節點輸入）。
