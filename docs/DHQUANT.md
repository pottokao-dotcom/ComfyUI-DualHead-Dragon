# dhquant：DiT 感知的 TE／雙頭龍量化工具

> 狀態：研發中（2026-09-26 起）。這份是**長期方法手冊**：方法、驗證過的事實、踩過的坑、工具、路線圖。
> 每條結論都標了 **【實測】** 或 **【推論】**。推論沒驗過不准當結論用。
> 原始數據：`docs/sens/`；逐日細節：`docs/QUANTIZATION.md` 第 9–11 節。

## 0. 怎麼用（`tools/dhquant.py`，在 gx10 上跑）

```
cd ~/sens2/dh_v2 && PY=~/ComfyUI/.venv/bin/python3.12
$PY tools/dhquant.py list                              # 有哪些模型、庫裡有什麼、驗過的分數
$PY tools/dhquant.py curve qwen3-4b                    # 大小 vs 預測誤差（只讀表，幾秒）
$PY tools/dhquant.py run   qwen3-4b --preset q4_k_m    # 掃描（有就跳過）→ 分配 → 建 GGUF → 真實驗收
$PY tools/dhquant.py plan  qwen3-4b --budget-gb 2.7    # 任意大小；--aggressive 允許低於底線
```

- **預設名稱＝使用者定義**：`--preset q4_k_m` ＝ 和原版 Q4_K_M 一樣大、任何張量不低於 Q4（q5_k_m、q6_k 同理）。預算照 llama.cpp 的 use_more_bits 規則算。
- **敏感度庫 `sensbank/<模型>_<sha前8碼>/`**：`fisher.json`（每張量×每格式×每把尺）、imatrix、prompts、`manifest.json`、`configs/`、`builds/`（每個建過的 GGUF 的 sha256、配置、預測、實測）、`verified.json`。**掃過的模型不重掃**（`--force` 才重來）。
- **記憶體護欄**：每個 GPU 步驟都有看門狗，可用記憶體低於 `--reserve-gb`（預設 40，gx10 規則）就砍掉子程序，不會拖垮機器。
- **新增模型**：在 `tools/dhquant_models.json` 加一筆（權重路徑、DiT 輸入層檔案、imatrix、各尺權重）。8B 目前能 scan/plan/curve；build/verify 還沒接（gx10 沒有 8B BF16 GGUF、sens_dit 驗收只認 4B 讀取層）。
- 端到端實測（4B，`run --preset q4_k_m`）：2.497 GB，Z-Image 10.0%／klein 6.6%／pad 27.0%（原版 Q4_K_M 11.5／8.3／32.4），和手動流程結果一致。

## 1. 為什麼要有這個工具

文字編碼器（TE）的量化，市面上的做法（llama.cpp 預設 Q4_K_M、Unsloth Dynamic）都是**照 LLM 的輸出（下一個字的 KL）**來決定哪層保留精度。但 TE 接 DiT 時，DiT 讀的是**某幾層的隱狀態**（Z-Image 第 34 層、klein 第 8/17/26 層、QI2.1 最後一層），它在意的東西完全不同：
- 讀取點之後的層對編碼沒有影響；
- 讀取點正前方幾層最要緊；
- klein 會讀 pad，而 pad 的品質在前 8 層就定型了。

這些只有「用 DiT 真正讀到的東西來量」才看得到。**這是我們的護城河。**

**適用**：模型要當 TE 或雙頭龍，而且檔案會重複使用或發布。
**不適用**：純 LLM 聊天，直接用 Unsloth 或 Q4_K_M 就好。
**最終門檻**：出圖 A/B 要看得出差別，否則不值得做。
**成本規格**：一顆 4B／8B 從頭到尾 ≤ 30 分鐘（使用者定）。今天花掉的時間是一次性的研發成本。

## 2. 兩把量尺

| 量尺 | 量什麼 | 用在哪 |
|---|---|---|
| **DiT 量尺**（`tools/sens_dit.py`） | 讀取點的隱狀態，過 DiT 自己的文字輸入層（Z-Image `cap_embedder`、klein `txt_in`＋LayerNorm、QI2.1 `txt_in` MLP）之後，跟 bf16 的相對誤差 `rel_dit` 和 1−cos | TE（**主要目標**） |
| **PE 量尺**（`tools/sens_pe.py`） | 真實擴寫樣本逐字比對：KL、選字不變率 | 擴寫（**只當門檻**） |

- 優先順序是 **TE 優先、PE 保底**（使用者定）。PE 的錯誤大多是換個說法，看得到也救得回來；要防的是大錯：格式壞掉、該逐字照抄的文字沒照抄、重複、換語言。
- 只有 PE 會用到的層（讀取點之後），有 PE 保底格式就好。

**【實測】原始 cos 會騙人。** Qwen 殘差流有少數巨大通道（Z-Image 第 0/4/56 維，是中位數的 76/91/22 倍），cos 被它們主導。4B 全 Q4_K：原始 cos 0.995，過 DiT 輸入層後誤差 12.4%。但 **8B QI2.1 相反**：它的 txt_in 反而會吸收誤差（原始 cos 0.986，過輸入層後 0.9989）。⇒ **一律看過輸入層之後的分數，而且每個模型都要量。**

## 3. 數學模型

**【實測】傷害可以相加。** 4B 每次只壓一組、各組傷害加總，和整份一起壓的實測值比較：Z-Image 差 3%、klein 真 token 差 4%。

> 總傷害 ≈ Σ 敏感度 S × 權重誤差 E(格式)

- **E（這格式把這個張量的權重壓壞多少）**：只看權重、不跑模型，幾秒鐘就算完（`tools/weight_err.py`，要用 imatrix 加權）。
- **S（這個張量被下游放大多少）**：每個模型只要量一次。今天是用 Q4 逐層掃描量的；工具化時改成梯度（Fisher）一次反向傳播。
- **例外**：誤差大時（klein pad、2–3 bit）1−cos 會飽和，加總會高估（pad 高估 2 倍）。這種情況只拿來排名次，最後整份實測驗收。
- **rel ≈ √(1−cos)**：rel 要減半，得消掉約 75% 的傷害。所以只救少數幾層看不到大改善。

**【實測】最前面那幾 bit 最值錢。** 權重誤差對 Q4_K 的比例：Q5_K 0.26、Q6_K 0.063、Q8_0 0.006。也就是 Q4→Q5 消掉 74% 的傷害，Q5→Q6 再 19%，Q6→Q8 只剩 6%。真實 GGUF 驗證（第 34 層）：Q6 +19 MB 就拿到 F16（+138 MB）91% 的改善。
⇒ **保護的層升到 Q6 就夠；F16／Q8 幾乎不划算。**（使用者曾假設讀取點用 F16 超值，被實測否定。）

## 4. 分配：在預算內買最多精度

`tools/alloc.py`：每個張量（或組）先放在底線格式，再依「每 MB 能消掉多少傷害」往上買，買到預算用完為止。不需要定義「多敏感才算敏感」，**由預算決定**。
- 候選格式：IQ3_S、IQ4_XS、Q4_K、Q5_K、Q6_K（Q8／F16 只在數據證明值得時才開放）。
- 底線依策略：保守 Q4_K、平衡 IQ4_XS、激進 IQ3_S（只給最不重要的）。
- 多個產品共用一份檔案（Z-Image＋klein 都是 Qwen3-4B）：每個產品的傷害正規化後加權合併。

**【實測】踩過的坑（第一版輸的原因）**
1. 只允許 Q4→Q8：錯過最值錢的第 5 bit。同 2.9 GB，Unsloth Q5 6.1% 對我們 9.4%。
2. **粒度太粗**：把 q/k/v/o 綁成一組、gate/up/down 綁成一組。Unsloth 是按張量種類分配：attn_v 幾乎全 Q6（它很小，升級幾乎不花空間），ffn_down 大量 Q6，attn_output 從不升。⇒ **分配必須到張量層級**（測法見第 5 節）。
3. 目標權重沒配好：klein pad 份量太重，Z-Image 分到的太少。

## 5. 量測流程（一顆新模型）

1. **imatrix**：用真實會編碼的文字校準（擴寫後的長 prompt），不是 system prompt。【推論：應該比較好，待驗】
2. **層敏感度**：一次逐層掃描（或梯度）。
3. **張量種類比例**：7 次（每種張量在所有層一起壓），假設「層 × 種類」可以分開相乘。【推論，待驗】
4. **格式係數**：`weight_err.py`，不跑模型。
5. **分配**：`alloc.py`。
6. **真實 GGUF 驗收**：`tools/gguf_cfg_gx10.sh`，經過雙頭龍引擎，對照 comfy 官方 bf16。**只有這一步的數字算「驗過」。**
7. **出圖 A/B**：最終門檻。

**【實測】模擬 vs 真實**：模擬（權重壓再還原，塞回 torch 模型）在 4 bit 級準（Q4_K_M：模擬 11.0%、真實 11.5%），在 Q8 級**低估約 1.5 倍**（模擬 1.3%、真實 2.1%）。原因是 llama.cpp 在權重為量化格式時，會把 activation 也量化成 8 bit。引擎本身的下限（BF16 GGUF）是 0.28%。
⇒ **模擬拿來排名和探索低位元；驗收一律用真實 GGUF。**

### 6b. 2026-09-27 凌晨【實測，真實 GGUF】

**DiT 加權 imatrix（`tools/fimat_to_gguf.py`，同一張 2.9 GB 型別表，只換捨入）**：原本 6.04/4.02/20.85 → λ=0.5 5.95/4.01/**20.20**、λ=1 **5.94/3.94**/20.70。只好 1–3%：在 Q5/Q6 精度，捨入不是瓶頸（llama.cpp 把 activation 壓 8 bit 的誤差和捨入無關）。加權向量用和驗收題不重疊的 36 題算（避免對考題調參）。

**Z-Image-Engineer V6（Qwen3-4B 微調，`sensbank/z-image-engineer-v6_1560f829`，只看 Z-Image 尺）**：

| V6 | 大小 | Z-Image |
|---|---|---|
| 原版 Q4_K_M（同 imatrix） | 2.50 GB | 10.6% |
| 2.9 GB，**直接共用 4B 原版的表** | 2.91 GB | 5.22% |
| 2.9 GB，**重掃 V6 自己的表**（13 分鐘） | 2.91 GB | **4.6%** |

- **變體共用敏感度**：V6 和原版的單張量排名 Spearman 0.92，V6 整體比原版不敏感約 15%。共用可用但損失約 12% → 出貨檔一律重掃，共用只當粗估。
- 修復 LoRA（`tools/repair_lora.py`）：底座＝GGUF 反量化的權重，目標＝bf16 的 DiT 輸入層輸出，損失＝量尺本身，掛引擎 enc_lora（只在編碼時）。**【實測】r16、1973 題 1 epoch（lr 2e-4，59 分鐘）：4.6% → 4.13%，LoRA 64 MB**（`models/loras/zimage_engineer_v6_dhq_2p9_repair_r16.gguf`）。同樣 64 MB 拿去買位元預測約 4.2% ⇒ **修復 LoRA ≈ 多買位元，只小贏**；訓練 loss 沒明顯下降。llama.cpp 的 activation 8-bit 誤差訓練時沒模擬到，補不了。【推論】要大降誤差主要靠位元；LoRA 可再試 Q8 存（32 MB）、更久/低 lr。

## 8. 跟 LoRA、節點的相容性

| 方法 | LoRA 要動嗎 | 節點要改嗎 |
|---|---|---|
| 張量級混精度、更好的取整（GPTQ／GSQ） | 不用 | 不用（就是標準 GGUF） |
| R2 旋轉（attention 內 v/o） | 只有 v/o 上的 LoRA 要轉 | 不用 |
| R1 旋轉（殘差流） | 所有 LoRA 都要轉（A·R，精確，不用重訓） | 小改：讀出的隱狀態轉回來，由 GGUF metadata 開關，舊檔不受影響 |
| 修復 LoRA | 多掛一顆 | 不用（llama.cpp 可同時掛多顆） |
| 硬體 NVFP4 | — | llama.cpp 用不到 FP4 tensor core，而且 activation 也會被壓，精度反而差 ⇒ **不做** |

- 旋轉對 NVFP4 反而有害（MR-GPTQ, ICLR 2026），對分組粗的 K-quant 可能有用。【推論，待驗】
- 2 bit 需要旋轉（QuIP#／QTIP）；TE 不適合壓到 2 bit。
